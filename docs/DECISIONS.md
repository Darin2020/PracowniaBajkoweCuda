# Architecture Decision Log

Short entries: date, decision, reason, consequences. Newest at the bottom. Claude Code appends new entries here.

## 2026-11-12 — Initial decisions (agreed with the owner)
See `docs/PLAN.md` §2 for the full table. Summary:
- Angular frontend with static prerendering per locale. ASP.NET Core backend in Clean Architecture. One container serving both.
- BFF cookie authentication (no tokens in the browser). Google + Facebook first, Apple when a domain exists. No Instagram (Meta removed consumer Instagram login in Dec 2024).
- Azure SQL for relational data, Blob Storage for images (private, served through an authorized endpoint). Gallery images are static assets.
- Orders are created only by an admin from the chat. No online payments. Payment instructions are a config template.
- Email: admin always notified, customer optionally (checkbox in the chat, asked on the first message), debounced digests through an outbox.
- Languages en/de/fr/es/pl, currency EUR, content edited in code (no CMS).
- Only strictly necessary cookies, so no consent banner is needed. Legal texts to be reviewed by a lawyer.
- Azure Container Apps + Bicep + GitHub Actions with OIDC. Staging (scale to zero, free SQL) and production (min 1 replica).

## 2026-11-13 — Phase 0: repository foundation

- **SDK pinning.** `global.json` pins the .NET 10 SDK (`10.0.100`, `rollForward: latestFeature`, no prereleases); every project
  targets `net10.0`. Reason: the plan fixes the target on .NET 10 LTS, and a newer or prerelease SDK installed side by side must not
  silently change analyzers or build behaviour. CI installs `10.0.x`, so local and pipeline builds use the same SDK line.
- **Classic `.sln`, not `.slnx`.** The plan and the documented commands name `BajkoweCuda.sln`; kept for the widest tooling support.
- **Tests: xUnit v3 on Microsoft.Testing.Platform.** xUnit v3 4.x no longer supports the VSTest target on the .NET 10+ SDK, so
  `global.json` opts in to the MTP runner. Consequences: the command is `dotnet test --solution BajkoweCuda.sln` (not
  `dotnet test BajkoweCuda.sln`); coverage and TRX come from `Microsoft.Testing.Extensions.CodeCoverage` / `.TrxReport`
  instead of coverlet. Assertions: Shouldly. Mocks: NSubstitute (as suggested in the plan).
- **Architecture tests from day one.** The first unit tests assert the dependency direction (Domain references only the BCL;
  Application references no outer layer, ASP.NET Core, EF Core or Azure SDK), so the rule in `CLAUDE.md` is enforced by CI.
- **Liveness endpoint runs no checks.** `/health/live` uses `Predicate = _ => false`, so health checks registered later
  (database, blob) can never leak into the probe and wake the serverless database. They belong to `/health/ready` (added with those dependencies).
- **Frontend.** Angular 22 (zoneless by default), Vitest (the default runner of this version), ESLint via `angular-eslint`,
  Prettier with `eslint-config-prettier`. Client-rendered for now; `@angular/ssr` prerendering and `@angular/localize` arrive in Phase 1.
- **Dev proxy also forwards `/health`** (besides `/api` and `/hubs` from the plan), so the proxy can be verified before any `/api` endpoint exists.
- **Compose.** Ports are bound to `127.0.0.1` only. The SQL Server `sa` password comes from `.env` and has no default, so no
  password is committed. The `app` profile is added in Phase 1 together with the `Dockerfile`.
- **CI.** Actions are pinned to commit SHAs with the version in a comment (Dependabot keeps them current). `ci.yml` also validates
  the compose file. CodeQL additionally scans the workflow files (`actions` language).
- **LICENSE** copyright holder is "Pracownia Bajkowe Cuda" (change it if a personal name is preferred).

## 2026-11-15 — Dependabot does not raise TypeScript on its own

- **Decision.** Dependabot ignores major and minor updates of `typescript` (patch updates still arrive).
- **Reason.** Angular pins the supported TypeScript range (`@angular/build` 22.2 requires `>=6.0 <6.1`). The first Dependabot PR
  bumped TypeScript to 7.0 and failed at `npm ci` with `ERESOLVE`.
- **Consequence.** TypeScript is upgraded manually, in the same change as the Angular major/minor that allows it.

## 2026-11-15 — Phase 1: public site, i18n, SEO, container

**Rendering and i18n**
- **Static prerendering through `@angular/ssr` with `outputMode: "static"`.** The build writes `browser/{locale}/...` with
  prerendered `index.html` files for the landing and legal pages and one client-side shell (`index.csr.html`) per locale.
  No Node server exists at runtime; the Express server generated by the schematic was removed.
- **One build per locale, locale in the URL.** `localize: true` in the production configuration; the dev server
  (`ng serve`) serves English only. The language switcher is a set of plain links (full page load) and stores the
  choice in the `lang` cookie, which the server reads for the `/` redirect.
- **Translations: XLIFF 1.2, own merge script, no extra dependency.** `npm run i18n:extract` re-extracts
  `messages.xlf` and `scripts/i18n-merge.mjs` rewrites the four locale files. The plan says `state="needs-review"`;
  the valid XLIFF 1.2 value is `needs-review-translation`, so that is what the initial machine translations carry.
  `i18nMissingTranslation: "error"` makes the build fail on an untranslated message.
- **`PUBLIC_BASE_URL` is a build-time input** (canonical/hreflang/Open Graph URLs, `robots.txt`, `sitemap.xml`), as the
  plan specifies. **Open issue for Phase 2:** this bakes the origin into the image, which conflicts with
  "build once, promote the same digest" across staging and production (different origins, and staging needs
  `Disallow: /`). Options: replace a placeholder origin when the app starts, or serve `robots.txt`/`sitemap.xml`
  dynamically from configuration. To be decided with the owner before the CD pipeline is built.

**Content-Security-Policy**
- **`script-src 'self'` with no exceptions.** To get there:
  incremental hydration is off (`withNoIncrementalHydration()`), because it enables event replay, which injects inline
  scripts; critical-CSS inlining is off (`inlineCritical: false`), because it adds an inline `onload` handler.
  The only inline `<script>` elements left are data blocks (JSON-LD and Angular's transfer state), which CSP does not
  treat as script.
- **`style-src 'self' 'unsafe-inline'`.** Angular puts component styles into `<style>` elements, both in the prerendered
  HTML and at runtime. Removing `'unsafe-inline'` needs a per-request nonce, which static HTML files cannot carry
  without server-side templating. Accepted for now; revisit in Phase 6 (security hardening). *(Replaced in Phase 6 by a per-response nonce, see the 2026-11-24 entry.)*
- **The CSP gate in CI is Lighthouse's `errors-in-console` audit**: a CSP violation is a console error, so the build fails.

**Hosting in ASP.NET Core**
- **A small middleware rewrites paths; the static file middleware sends files.** `/` redirects (302, `no-store`,
  `Vary`) by cookie, then `Accept-Language`, then English. `/{lang}/page` maps to the prerendered file when it exists,
  otherwise to that locale's client shell. A path whose last segment has a dot is treated as an asset and is a 404 when
  missing, never the HTML shell. `/api`, `/hubs` and `/health` are never rewritten.
- **Soft 404 for unknown pages.** An unknown path under `/{lang}/` returns the client shell with status 200 and the
  Angular "not found" page marks itself `noindex`. A real 404 status would need the server to know the client routes.
- **API 404 and content negotiation.** JSON clients get RFC 7807 ProblemDetails. A browser (`Accept: text/html`) gets a
  plain-text 404, because the ProblemDetails writer honours `Accept`. Either way it is never HTML.
- **Cache headers:** HTML `no-cache`; hashed `.js`/`.css` bundles `immutable` for a year; everything else one hour.
- **Response compression (Brotli/gzip) for the static text types only.** JSON is excluded so that compression side
  channels (BREACH) stay away from user-specific API responses.

**Container**
- **Runtime image `aspnet:10.0-noble-chiseled-extra`**: no shell or package manager, non-root; `-extra` for ICU
  (the de/fr/es/pl cultures). Consequence: no in-container `HEALTHCHECK` (nothing to run it with); probes hit
  `/health/live` from outside.
- **The compose `app` service mirrors production restrictions**: read-only root file system, all capabilities dropped,
  `no-new-privileges`. CI starts the container the same way before the smoke test.
- **Tests are a build argument, off by default** (`RUN_TESTS`): CI runs them in dedicated jobs, so the image build does
  not repeat them.

**Placeholders (owner's tasks, PLAN §16)**
- Texts, prices, contact details (`hello@example.com`, a dummy phone number, generic social links) and all pictures are
  placeholders. The pictures are generated SVG illustrations, so `NgOptimizedImage` is used without AVIF/WebP variants
  until real photos arrive.
- "Sign in" and the "Order a toy" call to action lead to a short "accounts are coming soon" page until Phase 3.

**Local workflow on the owner's machine**
- Windows Smart App Control blocks freshly built .NET binaries, so backend tests run in the `dotnet/sdk:10.0`
  container and the application runs through `docker compose --profile app`. Nothing in the repository depends on this.

## 2026-11-16 — Phase 2: Azure and continuous deployment

**Owner's decisions**
- Region `polandcentral`. Both databases start on the free serverless offer (`sqlUseFreeOffer`); production can move
  to Basic (DTU) later (see docs/RUNBOOK.md §4 for what that takes).
- **The public origin is set when the app starts, not at build time** (deviation from PLAN §7, approved by the owner).
  Reason: one image digest is promoted from staging to production, and their origins differ. The Angular build writes a
  placeholder origin (`https://public-base-url.invalid`); the API replaces it in HTML, `robots.txt` and `sitemap.xml`
  when it serves them (`PublicSiteFiles`), from the `PublicBaseUrl` setting. The app refuses to start with an invalid value.
  This closes the open issue recorded in the Phase 1 entry.

**Application**
- **`Seo:NoIndex`** (staging) adds `X-Robots-Tag: noindex, nofollow` to every response and serves a `robots.txt` that
  disallows everything.
- **`/api/version`** is anonymous: the pipeline polls it to know when the new revision serves traffic, and the
  repository is public anyway.
- **Logging:** Serilog to the console (JSON outside Development), enriched with app version and environment; trace ids
  come from the current activity. OpenTelemetry to Application Insights is enabled only when its connection string is set.
  Probe requests to `/health` are not logged.
- **Forwarded headers** are enabled through `ASPNETCORE_FORWARDEDHEADERS_ENABLED` in the Container App, not in code:
  the app is only reachable through the ingress, so the proxy address does not need to be pinned.

**Infrastructure**
- **Two Bicep entry points:** `shared.bicep` (registry) and `main.bicep` (one environment), plus a module per resource
  type. Run-specific values reach the `.bicepparam` files through environment variables.
- **No secrets anywhere:** the app uses a user-assigned managed identity for the registry, storage, Key Vault and SQL.
  Storage has shared-key access disabled, SQL is Entra-only, the registry has no admin user.
- **Budget notifications go to the subscription Owners** (`contactRoles`) instead of an Action Group with an email
  address, so no personal address is stored in the repository or in GitHub.
- **Exactly one replica** (`maxReplicas: 1`): SignalR and the outbox worker run in-process (PLAN §10).
- **Deferred to the phase that needs them:** the migration job (Phase 3, with the first migration), alerts and the
  availability test (Phase 7), ZAP scan (Phase 6). The database user for the app identity is a documented manual step.

**Pipeline**
- **`cd.yml` runs after CI succeeds on `main`** (`workflow_run`), or manually with an optional image digest for rollback.
  The digest, never a tag, identifies the image after the build.
- **Two deployment identities.** The staging one deploys the shared registry and staging and can read production; the
  production one can only be used from the `production` GitHub environment, which requires a reviewer. Pull requests
  therefore cannot reach production resources. Both need "Role Based Access Control Administrator" because the templates
  create role assignments.
- **Identifiers are stored as GitHub secrets** (tenant, subscription, client ids, SQL admin object id). They are not
  credentials, but secrets are masked in the logs of this public repository.
- **Registry cleanup never deletes an image that an environment is running**, and stops if it cannot tell.
- **Dependabot ignores major versions of the `dotnet/sdk` and `dotnet/aspnet` images**: the project is pinned to .NET 10.

## 2026-11-17 — Phase 3: database, migrations and SQL access

**Owner's decisions**
- **SQL access through a group and a migration identity.** Each SQL server's Entra administrator is the group
  `sg-bajkowecuda-sql-admins-<env>` (the owner + `id-bajkowecuda-migrator-<env>`), created by
  `scripts/azure-bootstrap.ps1`. The migration job runs as the migrator; the app identity gets a database user with
  `db_datareader` + `db_datawriter` only, so the running app cannot change the schema. Rejected: making the app
  identity the server administrator (simpler, but full server rights for the internet-facing process).
- **Phase 3 is delivered in several PRs** (database → auth API + email → 2FA/admin/audit/deletion → OAuth → Angular),
  each deployed to staging.

**Implementation**
- **`ApplicationUser` lives in Infrastructure** (`Identity/`), not in Domain: it derives from ASP.NET Core Identity and
  the Domain layer has no framework dependencies. Domain entities will refer to users by id.
- **The app user is created with `CREATE USER ... WITH SID = <client id>, TYPE = E`**, not `FROM EXTERNAL PROVIDER`:
  the latter, run by a managed identity, needs Microsoft Graph permissions on the SQL server's own identity
  (Directory Readers), which a personal tenant would have to grant by hand.
- **Migrations run from the application image** (`dotnet BajkoweCuda.Api.dll migrate`), as a Container Apps job in
  Azure, as a one-shot `migrate` service in docker compose, and as a step of the CI image job. One image, no separate
  migration bundle.
- **Two-pass deployment:** the first Bicep pass updates the infrastructure and the job to the new image while the app
  keeps the running image, the job migrates, the second pass rolls the app out. New code never meets the old schema.
  Rollback consequence: migrations must stay compatible with the previous image (RUNBOOK §3).
- **The migrator and the SQL administrators group are created by the bootstrap script**, not by Bicep: Bicep cannot
  add group members without Microsoft Graph permissions, which the deployment identities do not have.
- **`/health/ready`** checks the database and is used only by the smoke test, never by container probes, so the
  serverless database can pause.
- **Integration tests use Testcontainers** (SQL Server 2025), one container per test run, a fresh database per test.
  Tests that need it carry the trait `Category=Database`; the optional test run inside the Docker build skips them.

## 2026-11-18 — Phase 3: accounts API, cookies and email

**Owner's decision**
- **The email dispatcher runs on a signal, not on a 30-second poll** (deviation from PLAN §3.6, approved by the owner).
  Production keeps one replica running, and a timer would stop the free serverless database from ever pausing
  (it pauses after 60 idle minutes): the free monthly allowance would be gone in two to three days. The dispatcher
  reads the outbox once at startup, when an email is queued (in-process signal) and when the next delayed email or
  retry is due (time kept in memory). Delivery stays reliable: queued emails are rows in the database and are sent
  after a restart.

**Implementation**
- **Auth endpoints are thin controllers over ASP.NET Core Identity** (`Api/Auth`), not Application handlers: they are
  adapters around `UserManager`/`SignInManager`, which belong to the framework. Application holds what other layers
  share: `AppError` (stable error codes) and the `IEmailOutbox` port.
- **Request shape is validated with data annotations** in the API (PLAN §4.2 suggests FluentValidation in Application;
  there are no Application handlers for auth). The password policy is Identity's, reported as
  `auth.password_rejected` with Identity's error codes.
- **No account enumeration:** register, resend-confirmation and forgot-password always answer 202. Registering an
  address that has an account emails its owner instead ("you already have an account"); the password is validated
  before the address is looked up, so both cases answer the same. Every failed sign-in, including lockout and unknown
  addresses (with a dummy hash check), is `401 auth.invalid_credentials`.
- **Signing in does not require a confirmed email**; `me` reports `emailConfirmed`, and the chat will require it (§3.2).
- **Cookies:** `__Host-bc.session` (HttpOnly, Secure, SameSite=Lax, sliding 14 days, at most 30 days after sign-in,
  security stamp checked every 30 minutes) and `__Host-bc.af` + readable `XSRF-TOKEN` for antiforgery. When the public
  origin is plain `http://` (local development only) the cookies are named `bc.session` / `bc.af` and follow the
  request scheme, because `__Host-` cookies must be Secure.
- **Antiforgery is checked by a small filter** on every unsafe controller request (`400 antiforgery.invalid`): MVC's
  `AutoValidateAntiforgeryToken` needs the view services, which the API does not register.
- **Controllers require a signed-in user by default** (`MapControllers().RequireAuthorization()`); a fallback
  authorization policy would also have turned every unknown path into 401 instead of 404.
- **Data Protection keys** (session cookies, antiforgery tokens, email links) live in Blob Storage
  (`dataprotection/keys.xml`), wrapped by the Key Vault key `dataprotection`, so sessions survive restarts and new
  revisions. The app identity has "Key Vault Crypto Service Encryption User" on that key only.
- **ACS sends with the managed identity**, which has the built-in "Communication and Email Service Owner" role on the
  Communication Services resource (ACS does not support custom roles).
- **Email texts** are `.resx` resources in Infrastructure (en source; de, fr, es, pl need review, like the site's
  translations). Links point to Angular pages in the recipient's language; those pages come with the frontend part.
- **MailKit 4.18**: 5.0 changed the send API, and nothing in 5.0 is needed.
- **Fixed in the tests:** the SQL Server container is created on first use, so test runs without Docker (the optional
  run inside the Docker build) work again.

## 2026-11-18 — Phase 3: admins, 2FA, audit log, rate limits, export and deletion

**Owner's decisions**
- **`Admin:Emails` comes from the GitHub secret `ADMIN_EMAILS`** of each environment (personal data, so not in the
  public repository). CD passes it to Bicep as a secure parameter; the app and the migration job read it from a
  Container Apps secret (`Admin__Emails__0`, a comma-separated list).
- **The Admin role is synced when a user signs in or confirms their email, and for everybody in the migration job**
  (deviation from PLAN §3.3 "at startup"): a sync at startup would wake the serverless staging database on every cold
  start. The list is the source of truth: a confirmed account with a listed address gets the role, every other account
  loses it (with a new security stamp, so open sessions re-read their roles within 30 minutes).
- **`POST /api/account/password` was added** (current + new password): PLAN §8.1 requires re-authentication for
  password changes, but §6 listed no endpoint. Changing the email stays out of scope (no endpoint, no page).

**Implementation**
- **Admin endpoints use the `Admin` policy**: the role plus the `amr=mfa` claim, which Identity adds after a second
  factor. Without it the answer is `403 auth.mfa_required`, so the frontend can send an admin to the 2FA setup.
  `Features:RequireAdminMfa=false` is accepted in Development only; the app refuses to start with it elsewhere.
- **2FA is TOTP for everybody who wants it, mandatory for admins.** Enabling it with a first valid code turns the
  current session into an `amr=mfa` session (keeping its sign-in time) and returns 10 recovery codes. A recovery code
  signs in through its own endpoint, `POST 2fa/recovery-login` (not a flag on `2fa/login`: CodeQL rightly dislikes a
  request value choosing the verification method). Between the
  password and the code, Identity's two-factor cookie is `__Host-bc.2fa` (SameSite=Strict, 5 minutes).
- **Audit log** (`AuditLog` table, bigint identity as order and paging cursor): registration, email confirmation,
  sign-ins and failed sign-ins (unknown addresses are stored masked), 2FA changes, password reset/change, failed
  re-authentication, export, deletion, role changes. Entries are written through their own `DbContext`, so writing one
  never saves the caller's pending changes. The client IP is recorded. No retention limit yet (Phase 7, with the lawyer).
- **Rate limits are in memory** (ASP.NET Core `RateLimiter`, configurable under `RateLimiting`): auth endpoints 10/min
  per IP (sliding window), resend/forgot 3/hour per IP, admin 300/min per admin, `429 rate_limited` with `Retry-After`.
  The per-address limit (3 emails/hour to one address) is applied where emails are queued and fails silently, so the
  answer reveals nothing. Enough for one replica per environment; several replicas would each allow the full limit.
- **Re-authentication** (delete, change password) checks the password with lockout counting, and answers
  `403 auth.reauthentication_failed`, not 401, because the session itself is still valid. Accounts without a password
  (external sign-in only) will re-authenticate with their provider in the next part.
- **Deletion anonymizes the user row instead of deleting it** (`IsDeleted`, email/name/password/2FA/logins/roles
  removed, new security stamp, locked out), because orders (Phase 5) must keep pointing to it. Queued and sent emails
  of the user and the IP addresses of their audit entries are removed. The "account deleted" email is queued without a
  user id.
- **Finished outbox rows are deleted after 30 days** by the dispatcher, so email addresses (also of deleted accounts)
  do not stay forever.
- **Authorization matrix test:** every controller endpoint must carry authorization metadata, anonymous endpoints must
  match a reviewed list, and every `/api/admin` endpoint must use the `Admin` policy.

## 2026-11-18 — Phase 3: sign-in with Google and Facebook

**Owner's decisions**
- **The OAuth client secrets live in Key Vault** (PLAN §8.5), as secrets `Auth--Google--ClientId` and
  `Auth--Google--ClientSecret` (later `Auth--Facebook--AppId` / `AppSecret`) in each environment's vault. The owner
  writes them with the "Key Vault Secrets Officer" role; the app reads the whole vault into its configuration at
  startup with its managed identity ("Key Vault Secrets User"). A secret added later takes effect at the next
  restart or deployment. If Key Vault cannot be reached, the app does not start (like a missing setting).
- **Two Google OAuth clients**: `bajkowecuda-prod` (production redirect URI only) and `bajkowecuda-staging-local`
  (staging, `localhost:8080`, `localhost:4200`), so the production secret never sits on a developer machine. The
  consent screen stays in "Testing" (listed test users only) until the custom domain exists (Phase 8).

**Implementation**
- **Providers are registered only when configured**; `GET /api/auth/providers` lists them for the buttons.
  Callback paths are the ASP.NET Core defaults `/signin-google` and `/signin-facebook` (outside `/api`, so the dev
  proxy forwards them too).
- **One callback, three modes** (`GET /api/auth/external/{provider}?mode=signin|link|reauth&returnUrl=`): sign in;
  link to the signed-in account (the provider's answer is bound to the user id, so it cannot be replayed in another
  session); re-authenticate before deleting an account without a password (valid 10 minutes, stored in the session
  cookie's properties). The callback answers with redirects to Angular pages (`?error=account_exists`,
  `login_in_use`, `external_failed`, `reauthentication_failed`), since the browser follows them, not the app.
- **Linking by email only when both sides vouch for it**: the provider says the address is verified (Google's
  `email_verified`; Facebook says nothing, so never) and the local account confirmed it. Otherwise the person signs in
  to the existing account and links from the account page (PLAN §3.2, against account takeover).
- **Every new external account goes through complete-profile** (`GET`/`POST /api/auth/complete-profile`), not only
  those without an email: the terms must be accepted and stored with their version, as for registration. The external
  cookie (`__Host-bc.ext`, 15 minutes) keeps the provider's answer meanwhile. An address the provider did not verify
  gets a confirmation email. Complete-profile answers `409 auth.account_exists` for a taken address: this reveals that
  an account exists, but only to someone who has just signed in with a provider and typed that address.
- **Return URLs** must be local paths (`/pl/chat`); anything else is dropped (open-redirect protection, PLAN §6).
- **The last way to sign in cannot be removed** (`DELETE /api/account/logins/{provider}` → `409 auth.last_login`).
- **Tests** use a fake remote handler registered as "Google" that does what an OAuth handler does on our side
  (correlation cookie, protected state, external cookie), so the whole round trip runs without Google.

## 2026-11-18 — Phase 3: Angular sign-in pages and the session in the browser

- **The session state is one service with signals** (`AuthService`: `user`, `loaded`, `signedIn`, `isAdmin`).
  `GET /api/auth/me` is asked once, in the browser only, after the first render (`afterNextRender` in `App`), so the
  prerendered pages never call the API (PLAN §4.4). The top bar of a prerendered page first shows "Sign in" and
  switches to the user menu when the answer comes. Guards wait for the same request.
- **Guards**: `authGuard` (signed in, otherwise `/login?returnUrl=`), `adminGuard` (role Admin; the second factor is
  enforced by the API, which answers `403 auth.mfa_required`), `anonymousGuard` (the sign-in pages send a signed-in
  user home), `sessionGuard` (pages opened from emails need the XSRF cookie before they POST).
- **One interceptor turns errors into `ApiError { status, code, errors }`**; pages show `errorMessage(code)`, a
  translated text per code (the server's title is never shown). 401 `auth.not_authenticated` outside `/api/auth/*`
  forgets the user and goes to the sign-in page with a return URL; 403 `auth.mfa_required` goes to the 2FA setup.
- **Return URLs are app paths** ("/chat") checked by the same rule as the API's; for an external sign-in the locale
  prefix is added ("/pl/chat"), because the API redirects the browser to it directly.
- **Where people land**: customers go to `/chat`, admins without 2FA to `/admin/2fa-setup`, other admins to
  `/account`. Until Phase 4, `/chat` is a placeholder that already needs a signed-in user and asks to confirm the
  email address first.
- **The confirmation page confirms with a POST from the page**, so a mail scanner that only fetches the link does not
  confirm anything.
- **The 2FA setup shows the key as text and as an `otpauth://` link**, which opens the authenticator app on a phone.
  No QR code for now: it would need a QR library, and the admins are one or two people. The recovery codes are shown
  once and can be saved as a text file made in the browser.
- **The user's language for emails is the locale of the page they register on**; the account page can change it.
- **Form styles are global** (`styles.scss`: `.page`, `.card`, `.field`, `.input`, `.alert`, ...), so each page stays
  under the component style budget.

## 2026-11-18 — Phase 4: chat model, uploads and file access

**Owner's decision**
- **Images are processed with SkiaSharp** (MIT), not ImageSharp (Six Labors split license, like the commercially
  licensed MediatR/AutoMapper) or Magick.NET (large native package, many formats we do not need). Version 3.119.x:
  the 4.x line was only days old. `SkiaSharp.NativeAssets.Linux.NoDependencies`, because the chiseled runtime image
  has no fontconfig.

**Implementation**
- **Domain**: `Conversation` (one per customer, started by the first message), `Message` (text up to 2,000 characters
  and/or up to 5 images; system messages carry an event type and a JSON payload that the client renders in the
  reader's language), `Attachment` (uploaded first, attached to a message when it is sent, only by its uploader and
  only once). Read state is kept per side (customer / studio), as PLAN §5 says. Broken rules throw
  `DomainException` with an error code (`chat.empty_message`, `chat.too_many_attachments`, ...).
- **Upload pipeline** (`POST /api/chat/attachments`, one image per request):
  - the type comes from the magic bytes only (JPEG, PNG, WebP);
  - limits: 10 MB and 40 megapixels (checked from the header, before decoding);
  - the EXIF orientation is applied, then the image is re-encoded to WebP: display copy at most 1600 px (quality 82)
    and thumbnail at most 480 px (quality 75). The re-encoding drops EXIF/GPS and anything hidden in the file; the
    original is not kept;
  - JPEGs are decoded already scaled down (in eighths, never below the target), so a 40-megapixel photo does not need
    160 MB of memory;
  - blob names are new random GUIDs, unrelated to the attachment id and never taken from the file name.
  The uploader needs a confirmed email address (chatting does, PLAN §3.2). Limit: 30 uploads per hour per user.
- **File access** (`GET /api/files/{id}` and `/thumbnail`): the uploader, the customer of the conversation the image
  was sent in, or an admin whose session meets the admin policy (2FA). Everyone else gets `404 files.not_found`, the
  same as for an id that does not exist. `Cache-Control: private, max-age=3600`.
- **Cleanup**: an hourly background job deletes uploads that were not sent within 24 hours (rows first, then blobs).
- **Account deletion** now deletes the conversation, its messages and all its images (also those the studio sent)
  plus the user's unsent uploads; blobs are deleted after the transaction commits. The data export lists the
  conversation with the image addresses.
- **Storage client**: `Storage:BlobServiceUri` with the managed identity in Azure, `Storage:ConnectionString` for
  Azurite locally and in tests (containers created on first use there; in Azure the infrastructure creates them).
  `/health/ready` checks the storage account too.
- **Tests** run against Azurite in Testcontainers. The Blob client takes the account name from the path only for IP
  addresses, "localhost" and the emulator's default ports, so the test fixture uses the container's IP address when
  tests run inside a container (host.docker.internal).

## 2026-11-20 — Phase 5: the order model

- **The state machine lives in the domain** (`Order`): Draft → AwaitingPayment → InProgress → Ready → Shipped →
  Completed, and Cancel (with a reason for the customer) from any status that is not final. Each step is a method that
  checks the current status, sets its timestamp and records an `OrderStatusChange` (the customer timeline and the
  audit trail); creating the draft is the first entry. A step from the wrong status throws `orders.invalid_transition`
  (the API will answer 409). Unit tests try every step from every status.
- **Edit rules**: title, description, price and reference image only before payment (Draft, AwaitingPayment); the
  internal note until the order ends; photos of the finished toy only while it is being made or ready (at most 20,
  "Ready" needs at least one and keeps at least one).
- **Money** is a value type: positive euros with at most two decimals, stored as `PriceAmount decimal(10,2)` and
  `PriceCurrency` (an EF Core complex property).
- **Order numbers** come from the SQL sequence `OrderNumbers` (shown as `BC-0012`); ids are GUID v7. A `rowversion`
  column gives optimistic concurrency between admins.
- **Deleting a customer account keeps their orders** (PLAN §8.6): the customer row stays anonymized, and the order loses
  its conversation and reference image through `ON DELETE SET NULL` (both are deleted with the account).
- **Images used by orders are never "abandoned uploads"**: the daily cleanup skips attachments referenced as order
  photos or reference images.

## 2026-11-24 — Phase 6: ZAP baseline in CD, CSP without 'unsafe-inline', cross-origin isolation

- **ZAP baseline after every staging deployment** (`zap` job in `cd.yml`): a passive scan of `/en/` with the ZAP image
  pinned by digest. The HTML and JSON reports are an artifact, the alerts are listed in the job summary, and a
  high-risk alert fails the job, which holds back production (`production` needs `zap`). Informational rules that
  are false positives for this site are ignored in `.zap/rules.tsv`, each with its reason.
- **`style-src 'self' 'nonce-…'` instead of `'unsafe-inline'`.** The Angular build writes a placeholder into every
  HTML file (`ngCspNonce` on `<app-root>`, which Angular copies as `nonce` onto its `<style>`, `<link>` and `<script>`
  elements, and uses for the styles it adds at runtime). `HtmlPageMiddleware` replaces the placeholder with 128 random
  bits per response, and the CSP header carries the same value. Style *attributes* in markup are therefore not
  allowed; the templates have none, and Angular's `[style.x]` bindings use the CSSOM, which CSP does not restrict.
  Lighthouse's console check in CI fails the build if a style is blocked.
  - Cost: HTML pages no longer have `ETag`/`Last-Modified`, so a revisit downloads the page again instead of getting
    a 304. The pages are a few kilobytes and compressed; the hashed bundles keep their year-long caching.
- **`connect-src 'self'`** without `wss:`: in CSP Level 3 `'self'` also matches the same-origin WebSocket, which is the
  only one the app opens (SignalR). ZAP flagged the bare scheme as a wildcard.
- **`Cross-Origin-Embedder-Policy: require-corp` and `Cross-Origin-Resource-Policy: same-origin`** on every response:
  the site loads nothing from other origins (sign-in with Google is a top-level redirect, not an embed), and nothing of
  it should be embedded elsewhere, including the private images of `/api/files`.
- **Cookies reviewed on staging**: the session, antiforgery and 2FA cookies are `__Host-`, `Secure`, `HttpOnly`;
  `XSRF-TOKEN` is `Secure` and `SameSite=Strict` but readable by JavaScript, as the double-submit pattern needs. HSTS
  stays at the framework's 30 days on the Azure host name; a longer `max-age` (and `includeSubDomains`) comes with the
  custom domain in Phase 8.

## 2026-11-24 — Phase 6: load and abuse sanity checks

- **`scripts/abuse-check.sh <base-url>`** checks a running instance:
  - the request body limit;
  - anonymous uploads;
  - the sign-in rate limit with `Retry-After`;
  - a burst of 300 page requests, 25 at a time.

  It is not part of CI, because it uses up the sign-in limit of the calling address for a minute.
- **Findings, now fixed:**
  - The request body limit was Kestrel's default of 30 MB for every endpoint, including anonymous sign-in. It is now
    1 MB. The image uploads keep their own `[RequestSizeLimit]` (10.5 MB).
  - A body over Kestrel's limit was answered with a 500. It is now a 413 with `code: request_too_large`
    (`BadRequestExceptionHandler`).
- **`RequestSizeGuardMiddleware`** refuses a declared `Content-Length` over the endpoint's limit before anything reads
  the body, and closes the connection. Kestrel's limit stays as the backstop for chunked bodies. The guard also runs in
  the integration tests, which do not use Kestrel.
- **Results on the local `docker compose` app:**
  - 2 MB sign-in → 413;
  - 12 MB anonymous upload → 413;
  - the 11th sign-in within a minute → 429 with `Retry-After`;
  - a 1.9 MB image upload as a signed-in customer still works;
  - 300 page requests: all 200, p95 25 ms.
- **What this does not cover:** volumetric denial of service. That is left to the Container Apps ingress and, later,
  a CDN or WAF (Phase 8+). The rate limiter counts per replica in memory, which is enough while each environment runs
  one replica.
